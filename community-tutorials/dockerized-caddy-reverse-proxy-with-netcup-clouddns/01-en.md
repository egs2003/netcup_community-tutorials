# Introduction

[Caddy](https://caddyserver.com/) is a web server that obtains and renews HTTPS certificates automatically. When you point it at a domain, it normally proves ownership over HTTP (port 80). That approach has two limitations: it needs port 80 reachable from the internet, and it can't issue wildcard certificates (`*.example.com`).

Both limitations go away if Caddy proves ownership through a DNS record instead (the "DNS-01 challenge"): it creates a temporary `TXT` record, Let's Encrypt checks it, and then removes it again. This works even if your server has no public port 80/443 at all, for example behind a firewall that only exposes an internal network, and it's the only way to get a wildcard certificate.

This tutorial shows how to run Caddy in Docker as a reverse proxy in front of another container (as an example, a small demo web app), and how to configure it to solve the DNS-01 challenge automatically against a domain managed by **netcup CloudDNS**.

By the end of this tutorial, you'll have:

- A Caddy container that reverse-proxies HTTPS traffic to a backend container.
- A valid, auto-renewing Let's Encrypt certificate for your domain, obtained via DNS-01 against netcup CloudDNS.
- An understanding of when to reach for DNS-01 instead of the default HTTP challenge.

Reading time is about ten minutes; setting it up takes roughly 20–30 minutes, most of which is waiting for Docker to build.

## Requirements

- A server with Docker and Docker Compose installed (any current [netcup vServer](https://www.netcup.eu/vserver/) or [Root Server](https://www.netcup.eu/rootserver/) product works; this tutorial uses a **VPS 2000 G11** as an example).
- A domain registered with netcup that uses **CloudDNS** (rather than "classic" DNS). You can check this in the [Customer Control Panel (CCP)](https://www.customercontrolpanel.de/): open **Domains**, click the magnifying glass next to your domain, and look for a **CloudDNS** tab. If you instead see a **DNS** tab, your domain uses classic DNS — DNS-01 with the module in this tutorial won't currently work for it; see the note at the end.
- Basic familiarity with the Linux command line and editing text files (`nano` or `vi`).
- Basic Docker and Docker Compose knowledge (starting containers, editing a `docker-compose.yml`).

# Step 1 – Create a netcup API key for CloudDNS

netcup's DNS APIs authenticate differently depending on which system your domain uses. Since we're using CloudDNS, we need an **API Key** (not a "Legacy API Key" — that one is for classic DNS and won't work here).

1. Log in to the [Customer Control Panel (CCP)](https://www.customercontrolpanel.de/).
2. Go to **Master Data → API**.
3. In the **API Keys** section (not "Legacy API Keys"), click **Create API Key**.
4. Give it a short description (e.g. `caddy-dns-01`), accept the terms of use, and confirm.
5. Copy the generated key somewhere safe — you'll need it in Step 3, and it won't be shown in full again.

> **Info**
> If you're unsure which of your domains use CloudDNS, check each one individually in the CCP as described in the Requirements section. netcup is migrating domains to CloudDNS gradually, so older domains may still be on classic DNS.

# Step 2 – Build a custom Caddy image with netcup DNS support

Caddy's official Docker image doesn't include third-party DNS provider modules by default; they have to be compiled in using [xcaddy](https://github.com/caddyserver/xcaddy). The official image conveniently ships a `:builder` variant with xcaddy preinstalled, so we can do this in a small multi-stage `Dockerfile` without installing Go locally.

> **Info**
> At the time of writing, CloudDNS support for the `netcup` Caddy DNS module is a recent addition and not yet part of the upstream, officially released packages. This tutorial therefore builds against the author's own fork, which contains this support. Once the corresponding pull requests to [`libdns/netcup`](https://github.com/libdns/netcup) and [`caddy-dns/netcup`](https://github.com/caddy-dns/netcup) are merged and released, you should switch to the official module by removing the second `--with` line below — check the linked repositories for current status.

Create a new directory for your project and, inside it, a file named `Dockerfile`:

```dockerfile
FROM caddy:builder AS builder

RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    xcaddy build \
    --with github.com/caddy-dns/netcup=github.com/egs2003/caddy-dns-netcup@main \
    --with github.com/libdns/netcup=github.com/egs2003/libdns-netcup@main

FROM caddy

COPY --from=builder /usr/bin/caddy /usr/bin/caddy
```

What this does:

- The `builder` stage starts from Caddy's build image and compiles a custom `caddy` binary with the `netcup` DNS module linked in.
- The two `--with` lines both point at forks (`github.com/egs2003/...@main`) that add netcup CloudDNS support: the first tells xcaddy which Caddy module to include, the second is an xcaddy [replace directive](https://github.com/caddyserver/xcaddy#in-line-replacements) that swaps in the patched underlying library the first module depends on.
- The final stage starts from the plain `caddy` image and copies over just the compiled binary, keeping the resulting image small (no Go toolchain included).

# Step 3 – Write the Caddyfile

Caddy is configured through a file conventionally named `Caddyfile`. Create one next to your `Dockerfile`:

```caddyfile
your-subdomain.example.com {
	tls {
		dns netcup {
			api_key {env.NETCUP_API_KEY}
		}
	}

	reverse_proxy backend:80
}
```

Replace `your-subdomain.example.com` with your actual (sub)domain, and `backend` with the name of the container you want to expose (Step 4 sets one up as an example; adjust or remove this line if you're proxying to something else).

A few things worth understanding about this configuration:

- `tls { dns netcup { ... } }` tells Caddy to use the DNS-01 challenge with the `netcup` provider module, instead of the default HTTP-01 challenge.
- `api_key {env.NETCUP_API_KEY}` reads the API key from an environment variable at startup rather than hard-coding it into the file — we'll set that variable in Step 4. Never commit real API keys into a Caddyfile.
- Deliberately **not** set here: `customer_number` and `api_password`. Setting only `api_key` is what selects netcup's CloudDNS API in the underlying module; setting all three (`customer_number`, `api_key`, `api_password`) instead would select the older, classic DNS API, which doesn't work for CloudDNS domains.
- If your CloudDNS domain is brand new, propagation of the DNS-01 challenge record is quick (typically under a minute) — noticeably faster than netcup's classic DNS API in the author's own testing.

> **Info**
> Want a wildcard certificate instead (`*.example.com`)? Change the site address at the top of the Caddyfile to `*.example.com` (quote it if your shell or tooling requires that). The rest of the configuration stays the same — DNS-01 is a requirement for wildcard certificates, since the HTTP-01 challenge can't prove ownership of every possible subdomain.

# Step 4 – Set up Docker Compose

Create a `docker-compose.yml` in the same directory:

```yaml
services:
  caddy:
    build: .
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"   # enables HTTP/3
    environment:
      - NETCUP_API_KEY=${NETCUP_API_KEY}
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - backend

  backend:
    image: traefik/whoami   # small demo web app; replace with your real service
    restart: unless-stopped

volumes:
  caddy_data:
  caddy_config:
```

This defines two services: `caddy`, built from the `Dockerfile` in Step 2, and a placeholder `backend` service (a tiny web app that just echoes request information — swap this out for whatever you actually want to expose, e.g. a container running your own application). The `caddy_data` volume matters in particular: it's where Caddy stores obtained certificates, so they survive container restarts and rebuilds instead of being re-issued every time (which would otherwise risk running into Let's Encrypt's rate limits).

Next to `docker-compose.yml`, create a `.env` file with your API key from Step 1:

```
NETCUP_API_KEY=your-api-key-here
```

> **Info**
> Add `.env` to a `.gitignore` file if this project directory is (or will become) a git repository, so you don't accidentally commit your API key.

Your project directory should now look like this:

```
.
├── docker-compose.yml
├── Dockerfile
├── Caddyfile
└── .env
```

# Step 5 – Point your domain at the server and start the stack

Before starting the containers, make sure `your-subdomain.example.com` actually resolves to your server's public IP address. In the CCP, open your domain's **CloudDNS** tab and add an `A` record (and `AAAA`, if your server has IPv6) for the subdomain, pointing at your server.

> **Info**
> This is a separate step from the DNS-01 challenge: the `A`/`AAAA` record is what makes your site reachable for visitors; the `TXT` record Caddy creates automatically during certificate issuance is only used briefly to prove domain ownership to Let's Encrypt and is removed again afterwards.

Once the record has propagated (this is usually quick, but can take a few minutes), build and start the stack:

```bash
docker compose up --build -d
```

Watch the logs while Caddy obtains its first certificate:

```bash
docker compose logs -f caddy
```

You're looking for a line similar to:

```
{"level":"info","logger":"tls.obtain","msg":"certificate obtained successfully","identifier":"your-subdomain.example.com"}
```

If you instead see repeated `will retry` messages mentioning `netcup` or `solving challenges`, double-check the following, in order:

1. That `NETCUP_API_KEY` in `.env` is the **API Key** from the "API Keys" section of the CCP, not a "Legacy API Key" (they look similar but are for different systems).
2. That the domain in your Caddyfile really shows a **CloudDNS** tab in the CCP, not a **DNS** tab.
3. That the `.env` file is in the same directory as `docker-compose.yml`, and that you didn't wrap the value in quotes.

Once the certificate is issued, open `https://your-subdomain.example.com` in a browser. With the example `backend` service from Step 4, you should see a small page showing request details (hostname, IP, headers) — confirming that traffic is reaching the backend container through Caddy over HTTPS.

# Conclusion

You now have a Dockerized Caddy reverse proxy that automatically obtains and renews HTTPS certificates for a netcup CloudDNS domain via the DNS-01 challenge, without needing port 80 open to the internet, and with wildcard certificates available if you need them. From here, you can add more site blocks to the same `Caddyfile` for additional (sub)domains, each proxying to a different backend container on your Docker network — Caddy will obtain a separate certificate for each automatically.

If your domain instead uses netcup's classic DNS system (visible as a **DNS** tab rather than **CloudDNS** in the CCP), the module setup differs slightly: you'd configure `customer_number`, `api_key`, and `api_password` in the `tls dns netcup { ... }` block instead of only `api_key`, using a **Legacy API Key** and its associated password from the CCP. That configuration works with the officially released `netcup` Caddy module today, without needing the forks mentioned in Step 2.
